# GreenHouse Architecture Description

## 1) System Topology

- **Frontend**: PyQt5 desktop app in `frontend/`.
- **Backend**: Express monolith in `backend/`.
- **Messaging**: RabbitMQ for desktop command/response + internal auth notification events.
- **Data**: PostgreSQL for persistent entities, Redis for cache/operational keys.
- **Core Runtime**: external greenhouse core HTTP API (`GREENHOUSE_CORE_URL`, default `http://127.0.0.1:3001`).

## 2) Primary Runtime Flows

### A. Desktop command flow (RabbitMQ)

1. Desktop creates command envelope:
   - `commandId`, `command`, `type`, `parameters`, `sessionId`.
2. Desktop publishes to `greenhouse_commands` with `replyTo=command_responses.<sessionId>`.
3. Backend consumes with manual ack (`noAck: false`), validates, then processes through `CommandProcessor`.
4. `CommandExecutor` forwards greenhouse commands to core `POST /api/v1/commands/execute`.
5. Backend publishes response to `replyTo` when present (fallback `command_responses`) and only then acks message.

### B. Scheduling flow

1. Desktop writes schedules via REST `/schedules`.
2. Backend `SchedulesRuntime` loads enabled schedules and uses cron dispatch.
3. Runtime publishes command envelopes to `greenhouse_commands`.
4. One-time and recurring schedules update metadata/state differently (`completed`/`not_done` vs ongoing dispatch status).

### C. Auth + email verification flow

1. `POST /auth/register` creates user with `verified=false`.
2. Backend publishes verification event on `greenhouse.events.v1`.
3. Notification consumer sends email and retries via retry queue.
4. `GET /auth/verify-email?token=...` marks user verified.
5. `POST /auth/login` returns `403` for unverified users.

## 3) Backend Architecture

- `App` composes routers, service/repository layers, RabbitMQ consumer, schedules runtime.
- Core command path:
  - `CommandProcessor` - session queueing + cache/idempotency orchestration.
  - `commandCachePolicy` - TTL/stateful policy.
  - `redisCommandCache` - Redis read/write + idempotency helpers.
  - `CommandExecutor` - command routing to greenhouse core.
- Core proxy path:
  - `GET /status`, `/schema/getters`, `/schema/executors`, `/getters`, `/getters/:key`, `/executors`
  - `POST /api/executors/:name/:action` (`mode|on|off|set`)

## 4) Caching/Idempotency State

- Redis key format for result cache: `cmd:{sessionId}:{command}:{currentPath}:{sortedParametersJson}`.
- Idempotency key: `idem:{commandId}`.
- Current greenhouse command TTL map sets known commands to `0`.
- Effective behavior today:
  - stateful commands are never cached,
  - TTL=0 commands skip cache/idempotency path.

## 5) Frontend Architecture

- `main.py` enforces auth dialog before opening `GreenhouseDesktop`.
- `CommandWorker` runs RabbitMQ I/O in a background thread and emits Qt signals.
- Main UI mixins:
  - control commands,
  - server/core controls,
  - scheduling,
  - statistics,
  - edge/fog integration,
  - auth session behavior,
  - logic tab (local builder placeholder flow).
- Logic tab status:
  - local canvas model + validation + JSON preview is implemented,
  - backend/core logic API passthrough routes are not yet wired in backend.

## 6) Data Model

Persistent PostgreSQL entities:

- `users`, `devices`, `sensors`, `sensor_readings`, `actuators`, `schedules`, `sensor_alert_rules`, `sensor_alerts`, `user_logs`.

High-level relations:

- User -> Devices / UserLogs
- Device -> Sensors / Actuators / Schedules
- Sensor -> SensorReadings / SensorAlertRules
- SensorAlertRule -> SensorAlerts

## 7) Operational Notes

- Graceful shutdown handles HTTP server, RabbitMQ client, Redis, and PostgreSQL.
- Rabbit consumer prefetch is configurable (`RABBITMQ_CONSUMER_PREFETCH`, default `5`).
- Config values are env-based and loaded from repository root `.env` when available.
